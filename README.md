# Purchase-Time Delivery Delay Triage on Olist

IS5126 final project. The question: each evening an operations team can review at most 10% of the day's new orders, using only what was known at purchase. Which orders should it pick, and is acting at that point worth it? The project answers this with a time-ordered, leakage-safe evaluation on the public Olist dataset (99,441 orders), using a frozen research pipeline (`olist_delay`) and a read-only report layer.

**Read first:** [`docs/final-report.en.md`](docs/final-report.en.md) (also exported as [HTML](docs/final-report.en.html) and [PDF](docs/final-report.en.pdf)) and the deck [`presentation/slides.en.html`](presentation/slides.en.html) ([PDF](presentation/slides.en.pdf)).

## Headline results

| Result | Value |
| :--- | :--- |
| Main test (26 May–29 Aug 2018, `experiment-v2-002`) | Route late rate × promise tightness rule (`rule_region_lead`) beat 24 logistic-regression and tree models: 25.2% vs 21.0% validation recall. Backtest: 117 of 674 late orders caught, 17.4% recall, 6.2% precision (base rate 3.49%) |
| Regime shift | Early 2018 delays were cross-state; in the backtest, São Paulo → São Paulo orders promised within 10 days produced 41.4% of late orders |
| Second, pre-registered test (26 Oct–31 Dec 2017, `experiment-v3-late2017-001`) | The 60-day route rule won: 21.1% recall, 21.6% precision (base rate 10.0%), +7.7 points over the original rule. Models again did not beat the rules |
| Shipping-limit signal | 19.4% precision in 2018 (found post hoc), 28.9% on the unseen late-2017 window |

## Data and license

`data/` holds the unmodified [Brazilian E-Commerce Public Dataset by Olist](https://www.kaggle.com/datasets/olistbr/brazilian-ecommerce), redistributed under its [CC BY-NC-SA 4.0](https://creativecommons.org/licenses/by-nc-sa/4.0/) license. The data is © Olist; it may not be used commercially.

The run directories under `artifacts/runs/` (about 1.2 GB) are not in this repository. Without them, `verify`, `recompute_results.py` and the report rebuilds need a fresh pipeline run (see below); `check_docs_consistency.py` works from a clone because the cited `report_facts.json` files are tracked.

## Setup

Verified on Windows 11 x86_64 with Python 3.14.7.

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-lock.txt
.\.venv\Scripts\python.exe -m pip install --no-deps -e .
```

PDF export additionally needs `pandoc` on PATH and Microsoft Edge or Google Chrome.

## Common commands

Run from the project root with `$py = '.\.venv\Scripts\python.exe'`.

| Purpose | Command | Measured time |
| :--- | :--- | ---: |
| Unit tests | `& $py -m pytest -m unit` | about 25 s |
| Integration tests | `& $py -m pytest -m integration` | about 135 s |
| Verify the formal run (read-only) | `& $py -m olist_delay verify --run-id experiment-v2-002 --no-update-manifest --check-docs` | about 4 s |
| Independent recomputation | `& $py scripts/recompute_results.py --run-id experiment-v2-002 --output artifacts/evaluations/recompute.json` | about 5 s |
| Rebuild report facts and figures | `& $py scripts/report_analysis.py --replace`, then `& $py scripts/robustness_analysis.py --replace` | about 80 s + 60 s |
| Check narrative documents | `& $py scripts/check_docs_consistency.py` | under 1 s |
| Rebuild the HTML deck | `& $py scripts/build_presentation.py` | under 1 s |
| Export HTML/PDF | `& $py scripts/export_documents.py` | about 5 s |
| Full acceptance and delivery package | `powershell -ExecutionPolicy Bypass -File scripts/acceptance.ps1` | about 10 min |

Re-running the research pipeline from scratch takes considerably longer. Existing run directories are immutable, so use a new `--run-id`:

| Stage | Command | Recorded time / peak memory |
| :--- | :--- | ---: |
| Prepare data | `& $py -m olist_delay prepare --config configs/research-v2.json --run-id <new-id>` | 418 s / 605 MB |
| Smoke backtest | `& $py -m olist_delay backtest --config configs/smoke-v2.json --run-id <new-id>` | 372 s / 844 MB |
| Formal backtest | `& $py -m olist_delay backtest --config configs/experiment-v2.json --run-id <new-id>` | 740 s / 860 MB |
| Second-period backtest | `& $py -m olist_delay backtest --config configs/experiment-v3-late2017.json --run-id <new-id>` | about 10 min |

## How the evidence fits together

1. **The formal run `artifacts/runs/experiment-v2-002` is the source of truth** (a fixed-code re-run of `experiment-v2-001` with byte-identical predictions); `experiment-v3-late2017-001` is the pre-registered second test. It is bound to its configuration, its input hashes and the source hash of `src/olist_delay/`. Changing `src/` invalidates that binding, and the acceptance gate checks it.
2. **`scripts/report_analysis.py` reads the run's per-order predictions and the raw tables** and writes `artifacts/analysis/experiment-v2-002-report/report_facts.json`; `scripts/robustness_analysis.py` does the same for the v3 runs. It stops if it cannot reproduce the run's headline counts exactly.
3. **`scripts/check_docs_consistency.py` requires every number in the narrative documents to match a fact or a config value**, and every figure link to resolve. `verify --check-docs` alone checks only five tokens.

The deviations of the first run from its configuration were fixed in code (bootstrap replicates, cost scenarios, the selection margin, model hash checks). [`docs/decision-log.md`](docs/decision-log.md) records each fix.
